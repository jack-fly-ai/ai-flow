# Module adapters

`src/adapters/index.ts` defines the `ModuleAdapter` contract (scope guards, pack check, phase snapshots, reviewed-surface exclusions) and `getAdapter(module)` dispatch. `viewersAdapter` (`src/adapters/viewers.ts`) is the reference implementation for an OHIF-style viewer monorepo: phase 2 changes must stay under the module's source directories, `.gitignore` and `.task-dev/` edits are ignored, and the pack `check` capability runs a configurable command (`TASK_VIEWERS_CHECK`) when set. Packs without a dedicated adapter fall back to `genericAdapter` — no scope guard and no automatic pack check, surfaced as a loud viewer warning with gate 4 as the only backstop. The generic path DOES enforce mechanically the operator-configured deny-list (`taskdev.forbidPaths` → `TASK_FORBID_PATHS`): paths that must never change in any run are rejected at phase 2 even without a dedicated scope guard, so gate 4 is not the only backstop for an unscoped pack. A dedicated adapter's allow-list is strictly stronger and the deny-list adds nothing there. Design pattern for a module WITHOUT a dedicated test area: scope from the pack's `domain/code-map.md` roots, strict phase-3 snapshots, and a manual-track `check` surfaced as a WARNING pass. A new module pack means a new `src/adapters/<module>.ts` plus a pack under `skills/task-dev/references/<module>/` with the seven-row capability table.

Post-review code drift is guarded in standard mode via the adapter: phase 3 snapshots the change surface before the agent runs and `assertPhase3Scope` fails the phase if it moved; before packaging, phase 4 byte-compares the final tree's reviewed surface against the trusted gate-2 snapshot the orchestrator writes into the run dir (`gate2-reviewed.patch`, outside the agent's workspace). The reviewed surface is the adapter's `phase4Snapshot` — product code, with the module's test area excluded, because that area is allowed to evolve during phase 3 (`assertPhase3Scope` ignores it) and ships in the delivery tarball where the human audits it at gate 4. The agent-side gate-2 patch (`checkpoints/TASKxxxx_gate2.patch`, which becomes the deliverable CHANGES patch) stays the full tree diff. Replay mode gets the byte-exact equivalent from `task-replay verify`.

Upgrade note: `gate2-reviewed.patch` is written by whichever ai-flow version runs the pipeline. Runs that started on an older version (which snapshotted the FULL tree) keep working after an upgrade automatically: the orchestrator marks the surface it writes (`state.taskdev.gate2Surface = "product"`), and a legacy full-tree `gate2-reviewed.patch` without the marker is narrowed to its product sections (`filterPatchToProductSurface`, driven by the adapter's `productSurfaceExclusions`) before the phase-4 byte-compare — phase-3 test-area evolution does not false-fail an upgraded run, so no reset is required.

The delivery tarball is written to `~/task/TASK<id>_<Beijing timestamp>.tar.gz` (`TASK_PACKAGE_DIR` overrides the directory, used by tests). `.task-dev/` state and pipeline runtime files are never packaged. After a successful phase 4, older tarballs of the same ticket are moved to `<packageDir>/archive/` (never deleted — an old run record's download keeps resolving its archived path), so the delivery root shows exactly one current tarball per ticket.
