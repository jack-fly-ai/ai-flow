# Run reference

ai-flow is **Linux-only**: the run-lock stale detection reads `/proc/<pid>/cmdline`, stop/reset rely on `pkill`, and the ref-lock semantics assume POSIX. `src/cli.ts` fails fast on other platforms.

From the repository root, after `pnpm install` and `pnpm run build`:

```text
node ai-flow/dist/cli.js run 12345
node ai-flow/dist/cli.js status
node ai-flow/dist/cli.js ui
```

`npm run ai-flow -- run 12345` from `ai-flow/` runs the TypeScript sources without a prior build. Run ids are numeric GitHub issue numbers only — prefixes such as `TASK` or `#` are rejected. The status page is served at the `ui.host`/`ui.port` set in `ai-flow.config.json`. It lists `.ai-flow/runs/`, and the issue list (the default view) is the single place to start a local run: an open issue's **Start** button launches it with the configured default model. It can **Retry** a failed run from the failed stage, can **Approve** or **Reject** a run that is awaiting review (approve answers an open escalation, or passes gate 4 and downloads the package), can download the delivery tarball when `artifacts.package` exists, and offers a **Manage MCP** main view (operator-only) that edits the configured agent's MCP server list. There is no generic "Create task" form — runs are always started from a synced issue. It does not submit git or write back to the ticket system via github-mcp. Manage MCP is operator-only: the human edits the agent's MCP config through the UI; the agent never modifies its own MCP list (that would break the isolation guarantees in the hard rules). With `auth.tokens` configured (isolation edition) the viewer first shows a sign-in gate: a user identity sees and can act on its own runs only, the operator tenant sees every run and keeps Manage MCP; the CLI needs `AI_FLOW_TOKEN` exported for `run`/`status`/`stop`/`reset`.

Run `node ai-flow/dist/cli.js init` (or `npm run ai-flow -- init` from `ai-flow/`) at the repository root. It asks which agent to use — Cursor, Claude Code, ChatGPT, or DeepSeek — then which model, and writes `ai-flow.config.json`. Non-interactive: `ai-flow init --agent cursor --model composer-2.5 --yes`. The file stores `agent` and `model`; the command line for that agent lives in `src/agents/agents.ts`. A file that only has the older `runner.command` array still runs, and a re-init preserves it (together with user-set `runner.modelFlag` / `modelsCommand` / `statusCommand` / `versionCheck`): a previous command counts as custom when it carries a prompt token, belongs to the same agent (or to a legacy file with no `agent` at all), and differs from the preset's own template (bin path aside); switching to a different agent never preserves the old command. Tokens in that command are `{promptStdin}`, `{promptArg}`, `{promptFile}`, `{cwd}`, and `{model}`. `runner.modelFlag` defaults to `-m`; `runner.modelsCommand` and `runner.statusCommand` are optional commands the viewer uses for the model dropdown and status bar. `taskdev.skillDir` defaults to `skills/task-dev` (the task-dev skill is a separate repository — place it there, or point `skillDir` at it; the path is gitignored); `taskdev.pack` is the fallback module pack when phase 1 does not record one. The ticket is fetched by the agent through its configured github-mcp MCP — ai-flow no longer runs a separate MCP client, so there is no `mcp` config block. Do not commit cookies, and do not write them into `state.json` or logs (`src/auth/redact.ts`). The status bar shows this agent and model. Token counts come from `runner.statusCommand` when it is set.

There is no `CURSOR_API_KEY` and no `@cursor/sdk`. Any headless agent is a local process started by `src/agents/runner.ts`.
